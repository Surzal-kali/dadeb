# nvim scratch buffer lane (F2 → pyright, via generated tool stubs)

The F2 escape hatch (`tool_repl.py` cell → external editor) becomes a real
editing surface: nvim (LazyVim) attaches **pyright** to the temp cell, which
resolves the REPL's runtime-injected tool aliases from generated stubs — so
scratch cells get completion, hover (`K`), and signature help on `(` for
framework tools.

The tool wrappers only exist at runtime (`build_ipython_namespace` mints one
`async def` wrapper per discovered tool into the IPython `user_ns`), so the
editor can't see them by static analysis alone. This lane closes that gap.

> **Additive-only invariant:** every piece below is either a new file or a new
> line in a config file. `tool_repl.py` and `daharness/*` are never edited —
> the generator reads framework code, writes nothing back.

## Where things live (tracked vs not)

| Piece | Location | Git-tracked? |
| --- | --- | --- |
| Stub generator | `scripts/gen_repl_stubs.py` (this repo) | ✅ this repo |
| This catalogue | `nvim-scratch-buffer.md` (this repo) | ✅ this repo |
| nvim pyright wiring | `~/.config/nvim/lua/plugins/python.lua` | ✅ nvim config repo (`~/.config/nvim`), **uncommitted** |
| Generated stubs | `~/.local/share/framework-stubs/` | ❌ **not tracked anywhere** — regenerate, don't copy |
| PYTHONPATH export | `~/.zshrc` (last 3 lines) | ❌ dotfile, not in a repo |
| LazyVim python extra | `~/.config/nvim/lazyvim.json` `extras` list | ✅ nvim config repo |

The stub dir is disposable by design: it is fully derivable from the repo via
the generator. Nothing in it is hand-written, so git-tracking it would only add
drift.

## Root lane (sudo'd `tool_repl`)

The framework runs as **root**; `/root/.config/nvim` is symlinked to the kali
config for transparency, but the symlink does **not** cover everything this
lane wires. What root resolves depends on root's `$HOME`, so:

| Piece | Root sees | Works? |
| --- | --- | --- |
| `~/.config/nvim` (specs) | symlink to kali config | ✅ if symlink |
| Mason pyright | root's own Mason install (confirmed present) | ✅ |
| `~/.local/share/framework-stubs/` | `/root/.local/share/framework-stubs` | ❌ **missing → `nmap` undefined** |
| zshrc PYTHONPATH | root's own zshrc | ❌ not exported |

The signature-window piece (`blink.lua`) and the pyright spec both load through
the config symlink; the **stubs dir is the broken link** — `python.lua`
computes `vim.fn.expand("~/.local/share/framework-stubs")` at spec load, which
under root expands to a path that doesn't exist, so pyright's `extraPaths`
points nowhere and no tool alias resolves.

**Fix (one-time, keeps kali's stubs as single source of truth):**

```bash
sudo ln -s /home/kali/.local/share/framework-stubs /root/.local/share/framework-stubs
```

Root's pyright then sees the same regenerated stubs instantly — no second copy
to keep fresh. Optionally, for running the REPL's `from framework_tools
import *` as root:

```bash
echo 'export PYTHONPATH=/home/kali/.local/share/framework-stubs' | sudo tee -a /root/.zshrc
```

(Or symlink `/root/.zshrc` → kali's if the config-symlink policy extends that
far; kali-specific bits would leak, so an absolute-path export is the targeted
move.)

## Stub dir inventory (`~/.local/share/framework-stubs/`)

### `framework_tools.py` — PEP 562 shim (runtime side)

- Module docstring with the generation stamp (`Generated by scripts/gen_repl_stubs.py …`, date, tool count).
- `__all__` — every alias in sorted order (one per REPL-injected wrapper).
- `__getattr__(name)` — PEP 562 module hook:

  ```python
  def __getattr__(name: str) -> Any:
      _get_ip = getattr(builtins, "get_ipython", None)
      _ip = _get_ip() if _get_ip else None
      if _ip is not None and name in _ip.user_ns:
          return _ip.user_ns[name]
      raise AttributeError(...)
  ```

  `get_ipython` is a builtin only inside IPython, so inside the REPL every
  `__all__` entry resolves to the **live** wrapper; outside the REPL access
  raises a descriptive `AttributeError` instead of returning a silent `None`.
- No implementations. pyright types from the same-name `.pyi`; this file exists
  so `from framework_tools import *` executes clean in the REPL.

### `framework_tools.pyi` — type declarations (editor side, pyright consumes this)

One `async def` per alias, sorted:

```python
async def amass(target: str, options: str = None, scope_handle: str = None, scope_platform: str = None, **kwargs: Any) -> Any: ...
    """<verbatim _build_docstring output: capability, tool_id, transport,
    path, tags, Parameters, Next steps>"""
    # handles: ... | tags: recon.subdomain
```

- Signatures come from `tool_repl._build_signature` (required params first, no
  default; optional params default `None`), **plus `**kwargs: Any`
  permissively** — unknown kwargs go through preflight validation and get
  rejected there, but discovery occasionally surfaces params the static schema
  pass misses. Dropping `**kwargs` later is a free tightening (static arg-name
  checking) with no call-site churn.
- Docstrings are `tool_repl._build_docstring` verbatim — the same text
  `tool?` prints in the REPL.
- A one-line trailing comment carries `accepted_handle_kinds` and category
  tags for visual grep.
- Header: generation date (UTC), tool count, do-not-edit stamp.

## Regeneration

```bash
cd ~/github/stuff
./venv/bin/python scripts/gen_repl_stubs.py          # regenerate + print summary
./venv/bin/python scripts/gen_repl_stubs.py --check  # exit 1 if stale (CI-able)
FRAMEWORK_STUBS_DIR=~ elsewhere python scripts/gen_repl_stubs.py   # custom output dir
```

- Path taken: `tool_repl.discover_tools()` (the full static+dynamic scan, **no
  ChromaDB needed**) → `tool_repl.build_tool_aliases(manifests)` **verbatim**
  (curated `_TOOL_ALIASES`, auto-derivation, collision qualification — reused,
  never reimplemented, so stubs can't drift from what actually executes) →
  `_build_signature` / `_build_docstring` per alias.
- The `__all__` list and the `.pyi` defs are always from the same alias map, so
  the two files can't disagree with each other or with the live namespace.

## Scratch-cell convention (the two-line header)

```python
# vim: ft=python
from framework_tools import *
```

1. **Modeline** — prompt_toolkit's F2 temp cell doesn't get a `.py` suffix, so
   the modeline is what gives the buffer a python filetype; without it no Python
   LSP attaches, and nothing in the stubs matters.
2. **Star-import** — getattr's each `__all__` entry inside the REPL, and each
   one resolves through `__getattr__` to the live wrapper in `user_ns`. The
   alias is already in `user_ns`, so this costs nothing at REPL time; it exists
   so pyright sees the names and the header import never raises.

Notes:

- F2 opens a **real temp file**, so pyright attaches fine. A truly *untitled*
  buffer would not get LSP — hence modeline-on-a-file, not `:set filetype`.
- The shell that launches the REPL exports
  `PYTHONPATH="$HOME/.local/share/framework-stubs"` (`~/.zshrc`) so the header
  import resolves at runtime. nvim/pyright needs only `extraPaths` (next
  section) — the zshrc line is purely the in-REPL execution path.

## nvim wiring (`~/.config/nvim/lua/plugins/`)

**Two spec files**, both in the tracked nvim config repo:

### `python.lua` — pyright + stubs dir

```lua
local stubs_dir = vim.fn.expand("~/.local/share/framework-stubs")

return {
  "neovim/nvim-lspconfig",
  opts = {
    servers = {
      pyright = {
        -- lazy.nvim deep-merges with the python-extra's spec; extraPaths
        -- lands in the same settings tree the extra already owns.
        settings = {
          python = {
            analysis = {
              extraPaths = { stubs_dir },
              diagnosticMode = "openFilesOnly",
            },
          },
        },
      },
    },
  },
}
```

- The LazyVim `lang.python` extra (already in `lazyvim.json` extras) enables
  `pyright` via Mason; this spec only extends its settings.
- Same-name `.py/.pyi`: pyright resolves types from the `.pyi` automatically.
- `diagnosticMode = "openFilesOnly"` keeps background analysis off — diagnostics
  stay scoped to buffers you're actually in (scratch cells, stub consumers).

### `blink.lua` — the signature window (blink.cmp is opt-in!)

LazyVim's blink extra ships signature help **commented out** (experimental):
`-- signature = { enabled = true }` in
`lua/lazyvim/plugins/extras/coding/blink.lua`. Without this file, typing
`ssh_connect(` shows **nothing** — blink never requests
`textDocument/signatureHelp`, even though pyright serves it fine:

```lua
return {
  "saghen/blink.cmp",
  opts = {
    signature = { enabled = true },
  },
}
```

blink.cmp's own defaults then do the rest: `trigger.show_on_trigger_character
= true` auto-shows right after `(` / `,`; `show_on_insert_on_trigger_character`
re-shows when re-entering insert mode inside a call; `show_on_accept` can be
turned on additionally if you want it after accepting a completion.

### What this does NOT require

- **No Brain, no ChromaDB, no Ollama.** pyright reads the static stub files;
  the entire lane works with every framework service stopped. (Only *executing*
  a tool from the cell later hits the Brain socket — editing/typing never does.)
- **Restart required after adding specs**: lazy.nvim loads spec files at
  startup. If the nvim session predates `python.lua`/`blink.lua`, neither is
  active — restart nvim (or `:Lazy reload nvim-lspconfig` after re-opening the
  file) before concluding it doesn't work.

### Scratch-cell gotcha (top-level await)

IPython cells naturally contain top-level `await`; plain-Python pyright flags
it as `"await" allowed only within async function` — **cosmetic only**: its
semantic analysis still runs (verified: param-count `reportCallIssue`
diagnostics still fire on both sides of the syntax error). Completion,
hover, and signature help all work in cells with top-level `await`.

## Runtime truth vs LSP truth (why the header is not optional)

Two different scopes hold the tool names, and only one of them is visible to
pyright:

- **Runtime (the REPL):** `build_ipython_namespace()` injects every alias
  directly into `user_ns`. A bare `await nmap(...)` in any cell *just works*
  with no import — the names are already "imported" by construction.
- **Editor (pyright):** sees only the file text. Without
  `from framework_tools import *` in the buffer, pyright has no scope entry and
  `nmap` is genuinely undefined to it — regardless of the REPL being live.

So the header line is **for the LSP, not for Python**. And it isn't even a
lie at runtime: the PEP 562 shim resolves each `__all__` entry to the *same
live wrapper* already in `user_ns` (verified in an embedded shell), so the
import rebinds identical objects. Cheap at runtime, load-bearing in the editor.

**Debugging lesson (2026-10-10):** the entire lane was working while it looked
dead end-to-end — every "broken" session was just a buffer without the header.
Both the scratch lane and this doc now assume: *no header → undefined names is
correct behavior, not a bug.*

## Scratch-cell ergonomics (`~/.config/nvim/lua/plugins/scratch-cells.lua`)

Because "remember the header" is the failure mode that actually bites, the
editor side enforces it for you — **but the header is buffer-only, never on
disk**. prompt_toolkit's F2 reads the file back after `:wq` and pipes it into
the IPython cell; a header line in the file would execute (or fail) as cell
content, breaking the REPL.

The lifecycle:

1. **Open** (`BufReadPost`/`BufNewFile` on `/tmp/tmp*`) — header injected into
   the *buffer* + `ft=python` set. pyright sees it; the file on disk doesn't.
2. **Write** (`BufWritePre`) — format-on-save disabled for the buffer, then
   header stripped from the buffer before the file is written. The file on
   disk contains exactly what the operator typed.
3. **Post-write** (`BufWritePost`) — format-on-save restored, header
   re-injected so pyright keeps seeing it for continued editing.

> **Why format-on-save is disabled on write (2026-10-10 fix):** LazyVim's
> `conform.nvim` runs on `BufWritePre` and can reorganize imports — moving
> `from framework_tools import *` out of the header position into the
> script's import block. This corrupted the splice: `strip_header` (then
> using a fuzzy `find("framework_tools")` check) would match the relocated
> import line, then unconditionally delete lines 0–1 — which were *script
> content*, not the header. The fix: (a) `header_at_top()` does **exact line
> matching** against the known header, never a fuzzy substring search; (b)
> `strip_header` only fires when the exact header is at lines 0–1; (c)
> `format_on_save` is disabled on `BufWritePre` and restored on
> `BufWritePost`, so the formatter can't relocate the header between strip
> and re-inject.

Manual: `<leader>fc` / `:FrameworkCell` injects into any buffer (idempotent).
Opt out: `vim.g.fwcell_no_autostamp = true`. Disable: `vim.g.fwcell_disable
= true`.

> **ChromaDB is not the answer here.** ChromaDB powers tool *discovery*
> (semantic search); the header lane is purely an editor-side *typing*
> concern (pyright needs a file-scope import to resolve names that exist only
> in the REPL's `user_ns`). The two are orthogonal — ChromaDB being always-on
> doesn't help pyright see names in a file.

## Sanity checks (post-regen)

1. Scratch cell with the header → typing `ssh_` blink-completes `ssh_connect`
   etc. from the `lsp` source; `ssh_connect(` pops the signature window.
2. `:LspInfo` → pyright attached (check `extraPaths` in the client config).
3. In a live REPL: `from framework_tools import *` → no error; an alias
   resolves with `__manifest__` present.
4. `K` on an alias → the manifest docstring.
5. Header timestamp changes after re-running the generator; `--check` exits 0.

## Ground-truth diagnostic (when it "still doesn't work")

Run this **inside the failing buffer** (F2 cell, root or kali — whichever
session misbehaves), then paste the `DIAG:` output verbatim:

```vim
:lua dofile("/home/kali/github/stuff/scripts/nvim_lsp_diag.lua")
```

Read-only — prints HOME, buffer filetype + header lines, which stub paths exist
*for that process*, whether the spec files resolve, every attached LSP client
with its `extraPaths`, and whether the server returns `nma*` completions. Each
branch pins a distinct failure: missing stubs (root-lane section above), no
filetype (modeline missing), stale session (specs/extraPaths absent → restart
nvim), or a genuinely broken stub pair (re-run the generator).
