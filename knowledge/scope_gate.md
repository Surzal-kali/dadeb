# Scope Gate

## what it is

The scope gate (`utils/scope_gate.py`) is a framework-side backstop the
operator arms. State is persisted to `scope/.armed_packet_scope.json`
(mtime-checked every call, so changes apply inside a running Brain).
Arming is deliberately NOT exposed as an `@framework_tool` so no
model lane can ever toggle it.

## kernel wrappers (execute_code / REPL)

The Jupyter kernel namespace (same as the REPL) exposes scope wrappers.
`scope_on` and `scope_off` are deliberately NOT in the namespace —
they raise `PermissionError` if called. Arming/disarming is
operator-only via the CLI:

    python tool_repl.py scope on <handle> [--platform h1]
    python tool_repl.py scope off

- `scope_status()` — check armed state, loaded program/handle, asset
  counts, manifest age. Agent-callable — use this to verify the gate is
  armed before running offensive tools.
- `scope_search(query, platform="all", assets=False, ...)` — query
  bug-bounty boards for matching programs. Agent-callable for recon.

The wrappers are sync (not `await`ed) — they return printed output, not
transport envelopes.

## how it works

Every traffic-sending tool raises `ScopeGateError` on a blocked target. The
gate checks the armed scope file's mtime on every call — changes made in
the REPL take effect immediately inside a running Brain sidecar. The gate
covers all HTTP (gated_get, gated_request, session_get, session_post,
session_upload), all brute-force tools (ffuf, hydra, sqlmap), nmap/masscan,
and Metasploit dispatches.

## scope file format

`scope/.armed_packet_scope.json` — a JSON file with allowed targets (IPs,
CIDR ranges, hostnames) and optionally ports. The file is operator-authored
or generated by the REPL `scope on` command. See `scope/lab_local-lab.json`
for an example (dev tree; the deb seeds the same template into the state
root's `scope/` dir at install and keeps a copy at
`/usr/share/daharness/examples/scope/lab_local-lab.json`). Manifest files
are named `<platform>_<handle>.json` under `WORKSPACE_ROOT/scope/` — arm a
custom one with `scope on <handle> --platform <platform>`; a fresh
operator-authored manifest can be armed off rip without knowing the JSON
layout. `scope on` also accepts `--refresh` (fresh board fetch; custom/lab
manifests are plain files — the arm error names the exact path it looked
for, in plain `handle`/`platform` terms).

## where it enforces

- **Bridge lane** (OWUI `framework_run_tool` / gateway `/tools/execute`):
  every tool dispatch goes through the gate.
- **execute_code lane** (Jupyter kernel): the gate fires on every
  traffic-sending call inside the kernel — identically to the bridge. The
  kernel does not bypass the scope gate. `scope_status()` and
  `scope_search()` are bare callables; `scope_on()`/`scope_off()` are
  NOT in the namespace (they raise `PermissionError`). Arming/disarming
  is operator-only via the CLI (`python tool_repl.py scope on|off`).
- **REPL lane** (`tool_repl.py`): same enforcement — the REPL calls the
  same tool functions.
- **In-process fallback** (`daharness/executor.py`): when the Brain socket
  is down, tools run in-process with the same scope gate check.

## what it is NOT

The gate is never the legal basis, never a substitute for the agent's own
scope check. Default: NOT armed; nothing authorized until confirmed. The
agent must verify each action against documented scope before execute and
at every new target or changed objective, gate armed or not. Reachability
is not permission.

## tool-disable list (operator authority over non-traffic tools)

The scope gate governs **wire traffic** — it resolves target hosts/IPs
against the armed manifest. Offline compute (hash cracking, local
transforms) has no target IP, so the traffic gate never sees it. The
`disabled_tools` list is the operator's blunt brake for that gap: a
tool_id (or family prefix) the model may NOT dispatch while the scope is
armed.

- **Applies only while armed** — disarmed = lab = unrestricted. The disable
  list is an engagement-posture control, not a lab-mode control.
- **Same armed-state file** — `scope/.armed_packet_scope.json` gains a
  `disabled_tools: [<prefix>, ...]` key. Mtime-checked + atomic write +
  operator-only authority, all inherited for free.
- **Prefix matching** (identical to `TOOL_BUDGET_TERMINAL_ALLOWLIST`):
  trailing-dot family prefix (`payloads.hash_crack.`) kills the whole
  family; bare stem (`payloads.hash_crack.run_john`) is exact tool_id only.
- **Terminal-lane guard** — `scope disable utils.findings.` /
  `utils.memory_tools.` is refused without `--force` (a model that can't
  write findings or memory can't comply with anything).
- **`arm()` carries it forward** — re-arming after a manifest refresh
  preserves the disable list (the 2026-09-20 `--ip-boundary` drift shape).

CLI (operator-only, mirrors the existing scope verbs):

    scope disable <prefix> [<prefix>...] [--force]
    scope enable <prefix> [<prefix>...]
    scope disabled

`scope status` surfaces the disabled list so `scope_status()` (agent-callable)
lets the model SEE the posture it's operating under without being able to
change it.

Enforcement: two points, both verified in tree. (1) `daharness/executor.py`
preflight block — after manifest validation, before any dispatch; covers the
bridge lane, REPL, and kernel for both transports. (2) `listeners/thebrain.py`
CALL_TOOL handler — defense-in-depth for direct-socket callers that skip the
registry path. Both use the same mtime-cached `_load_state()`, so a REPL-side
`scope disable` is visible to a running Brain on the very next call.

What it is NOT: not hash-provenance enforcement (the list can't tell whether
a hash came from an in-scope dump), and not a cost limiter (one
authorized-but-huge hashcat run passes this gate and the tool budget
legitimately — authorization and budgeting stay separate knobs).
